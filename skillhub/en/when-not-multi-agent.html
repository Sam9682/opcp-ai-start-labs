When Not to Use a Multi-Agent Architecture

Afternoon · Design & Governance ⏱ ~5 min

Multi-agent systems are powerful, but they add coordination overhead, cost, and new failure modes. Often a single well-designed agent is the better engineering choice. This lesson gives practical guidelines for deciding.

Learning Objectives

  • Recognize the costs a multi-agent design introduces
  • Apply a decision checklist for single vs multi-agent
  • Default to the simplest architecture that works

The Hidden Costs of Multi-Agent

  • Coordination overhead — messages, handoffs, and shared state add latency and complexity.
  • Cost multiplication — each agent runs its own loop and consumes its own tokens.
  • Error propagation — one agent's bad output silently corrupts the next.
  • Harder observability — a failure is spread across several traces instead of one.
  • Emergent behavior — peer-to-peer agents can loop or deadlock in ways no single component intended.

Prefer a Single Agent When…

  • The task is essentially sequential and fits one agent's context.
  • Subtasks share most of the same tools and state.
  • Latency or cost budgets are tight.
  • You need a single, easy-to-audit trace (e.g. a regulated workflow).
  • The team is still validating the agent's reliability.

Consider Multi-Agent Only When…

  • Subtasks genuinely need different specializations or toolsets.
  • Independent subtasks can run in parallel for real speedup.
  • You want to enforce different permission scopes per role.
  • A single agent's context window cannot hold the whole task.

Decision Checklist

Rule of thumb: start with one agent. Split into multiple only when a concrete need — specialization, parallelism, or scope isolation — justifies the added cost.

Key Takeaways

  • Multi-agent adds coordination, cost, and new failure modes.
  • Default to a single agent; split only for a concrete, justified need.
  • Simplicity aids reliability, observability, and governance.
