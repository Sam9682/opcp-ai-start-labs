Stopping Criteria: Preventing Infinite Loops

Morning · Fundamentals ⏱ ~5 min

An agent that never stops is a liability: it burns tokens and money, hammers downstream systems, and can take destructive actions in a loop. A reliable agent always has well-defined stopping criteria. This lesson is the bridge between the morning theory and the afternoon's guardrails.

Learning Objectives

  • Explain why unbounded loops are dangerous
  • List the main categories of stopping criteria
  • Apply stopping criteria to an opcp-explorer deployment agent

Why Loops Run Away

Common causes of runaway loops:

  • Goal never satisfied — the success check can never be true (e.g., waiting for a status that will never appear).
  • Oscillation — the agent flips between two actions that undo each other (start → stop → start).
  • Repeated identical failure — the same tool call fails the same way, but the agent keeps retrying.
  • Degenerate planning — the planner keeps adding steps without converging.

Categories of Stopping Criteria

  1. Goal achieved — an explicit success condition is met (e.g., health check returns healthy). This is the ideal stop.
  2. Max iterations — a hard cap on loop turns (e.g., stop after 10 steps).
  3. Budget / cost limit — stop after N tokens, N tool calls, or a spend ceiling.
  4. Wall-clock timeout — stop after a fixed duration regardless of progress.
  5. No-progress detection — stop if the state has not changed, or the same action repeats, over the last K steps.
  6. Error threshold — stop after N consecutive or total failures.
  7. Human halt — a person or a guardrail (the kill switch) forces a stop.
Best practice: combine several criteria. Always pair the ideal stop (goal achieved) with at least one hard limit (max iterations or timeout) so the agent terminates even when the goal is unreachable.

Worked Example on opcp-explorer

A deployment agent tries to start an application and verify its health. Its stopping criteria:

stop when:
  health == "healthy"            # goal achieved
  OR attempts >= 5               # max iterations
  OR elapsed > 120s              # wall-clock timeout
  OR same_error repeated 3x      # error threshold
  OR operator_halt == true       # human halt / kill switch

With these in place, the worst case is bounded: the agent either succeeds, or stops within five attempts / two minutes and reports why.

Reporting on Stop

When an agent stops, it should report which criterion fired and the final state. "Stopped after 5 attempts; last error: build failed (missing dependency)" is actionable; silent termination is not. This report is also what you will annotate in the trace-reading lab.

Key Takeaways

  • Every agent needs explicit, enforced stopping criteria.
  • Pair a goal condition with hard limits (iterations, budget, timeout) and error/no-progress checks.
  • On stop, report which criterion fired and the final state.
